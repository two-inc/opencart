# Divergences from the reference plugin

Rows waiting to be filed in the Build Guide's divergence register (filed at P13, the release phase). PrestaShop is the reference for behaviour. Each row gives where the two plugins differ, what each does, and why.

| Area | PrestaShop behaviour | OpenCart behaviour | Reason |
|---|---|---|---|
| Admin, General: API key save | Saving the General tab verifies the submitted key against the submitted environment. A key Two rejects (401 or 403) is reverted to the stored key, but the environment is saved anyway. Any other failure (no answer, a 5xx) stores the submitted key with a warning. | The key and environment are one pair, saved together or not at all. A rejected or malformed key is never stored. A key Two could not judge replaces the stored key only when the stored key's last definitive answer from Two was not ok, so an outage during a save never swaps a verified key for an unverified one. | A key is only good against the environment it was issued for, so saving one half of a refused pair leaves the shop with credentials that cannot work. Keeping a verified key through an outage keeps Two at checkout. |
| Admin, General: API key field | The stored key is rendered back into the form. | The key field always renders empty, with a note that a key is saved. An empty field means "keep the stored key", and the live check then uses the stored key. | The key never needs to leave the server, so it doesn't. |
| Admin, Diagnostics: custom request headers | Rows are refused for an invalid name, a reserved name, a missing value or an invalid value. A second row with the same name is saved. Server-side calls then send both header lines; the browser-side header map keeps only the last row with that name. | The same four checks, plus a second row with a name already used is refused on save. | OpenCart's client sends the first row with a name and drops the rest, so a duplicate would be saved but not sent. A row the merchant sees saved should be a row that is sent, the reasoning PrestaShop applies to a row with no value. |
| Admin, Diagnostics: scheduled refresh URL | One refresh URL per shop, guarded by a token; on a multistore install each shop schedules its own line. | One URL for the install, guarded by a random token, with the same 15-minute floor and hourly-capped rejection log. OpenCart's own cron runner (`index.php?route=cron/cron`) also runs the refresh daily without the token, through the cron table row install() registers. | OpenCart keeps the extension's settings and merchant record once for the install, not per store, and ships a native cron runner, so a merchant whose crontab already calls it needs no second line. |
| Admin, Diagnostics: error log view | Lists the module's last 100 log rows of any severity and its last 50 discrepancy snapshots, each with a JSON download. | Shows the extension's last 100 lines of the shop's error log, with the API key and every custom header value redacted and each line escaped. No discrepancy snapshots. | OpenCart has no log table: the extension writes to the shop's error log file, read here from its last 2 MB. The plugin keeps no discrepancy snapshots to list. |
| Admin, Diagnostics: skip the confirmation token check, clear settings on uninstall | Two more switches: one skips the order-confirm token check (debug only), one decides whether uninstalling deletes the stored settings. | Neither switch. The confirmation return is always token-checked, and uninstalling always deletes the extension's settings, as OpenCart's own uninstall does for every extension. | A switch that turns off a security check has no place on a shop that can be debugged with the log instead. OpenCart 4.1's own Payments > Uninstall deletes the extension's settings (deleteSettingsByCode), so a switch to keep them could not be honoured. |
| Admin copy: environment help, title help, key help | Environment help names Production and Staging. Title help reads "which is appear on checkout page". Key help says "api key". The fulfilment help leaves a bracket unclosed. | Environment help names Production and Sandbox. The grammar, the capitalisation of "API key" and the bracket are fixed. | Merchants test against sandbox; staging is offered only on internal Two shops. The rest are typo fixes. |
| Order payload: shipping and charge tax | The carrier's stored tax amounts give the shipping line's tax. | OpenCart stores tax per product line and per rate for the order, but none for shipping, handling or the low-order fee. Those lines take the tax the shop's own tax engine gives their stored tax class at the order's addresses, and the default handler refuses the order unless the lines add up to the tax and total the shop charged. | It reproduces the merchant's own computation, the one OpenCart made at checkout, and is checked against what the shop actually charged, so the plugin never invents tax. |
| Order payload: discount tax | A cart rule is split across the rate contexts of the lines it applies to. | Coupon and reward-point discounts go as one line whose tax is what the shop's stored tax total leaves once every other line is counted. When the taxed lines carry more than one rate, the order is refused and the log names the reason. | OpenCart does not store how much of a discount's tax fell at each rate, and apportioning it would be the plugin deciding how tax is levied. |
| Order payload: fixed-amount tax rates | No equivalent: ecotax goes as its own line with a rate. | A line whose tax class holds a fixed-amount rate is refused, and the log names the line ("fixed-amount tax rate on <line>"). | A Two line carries one percentage rate, so Two would refuse the line; the plugin does not send what it knows will be refused. |
| Buyer cancels at Two's checkout | The order moves to the cancelled status map. | The Two order is cancelled and read back; the OpenCart order stays unplaced (status 0, a missing order) with a history note, and the buyer is back at the cart with the same cart. | Moving an OpenCart order off status 0 sends the buyer the order confirmation email, and an order the buyer never placed should not be announced as cancelled. |
| Admin, Order management: confirmed status | The verified status map may be any status, the branded Two state by default, whose own fallback is Preparation in progress. | A required map, Processing on a fresh install; an existing install (upgraded, or redeployed with `configure.php`) gets none and places at its default order status until the merchant saves one. The confirmed status and the fulfil, cancel and refund maps may not share a status: a save that would make them clash is refused on whichever side it changes, so the stored settings never clash. | OpenCart has no branded order states. Placing an order at a status the lifecycle acts on would fulfil, cancel or refund it the moment Two confirms it. |
| Admin, Order management: awaiting verification and payment error maps | Two more maps: the status an order waits at while the buyer verifies with Two, and the status it takes when the confirm-time lookup of the Two order fails. | Neither map exists. The order stays unplaced (status 0) until Two confirms it, and a failed confirm leaves it unplaced with a history note. | Moving an OpenCart order off status 0 sends the buyer the order confirmation email, so an order is placed only once Two has confirmed it (see "Buyer cancels at Two's checkout"). |
| Admin, General: vendor name | Free text, sent as the `X-Vendor-Name` header as typed. | Printable ASCII, at most 255 characters, checked on save. | It is sent as a header value: a line break or a non-ASCII character could not go on the wire. |
| Admin, Checkout fields: subtitle | Plain text and one link, stored with an English default in every language at install. | Plain text, escaped; no subtitle is stored at install, and a blank one shows none. | No link markup reaches the tile, so nothing needs a sanitiser. The brand declares no default tagline, and an English default would show in a non-English shop (see "Default payment method title"). |
| Admin, Checkout fields: explainer link | A question-mark icon whose hover box carries the explainer. | A text link, "What is Two?", whose tooltip carries the same explainer. | OpenCart themes have no icon set the extension can rely on; the copy and the target are the reference plugin's. |
| Admin, Checkout fields: order of the tile switches | Order intent, explainer link and tooltips sit above the optional field toggles. | The tooltips switch sits after the optional field toggles. | Its help text, the reference plugin's, refers to "the optional checkout fields above". |
| Validate tax subtotals off: the refund status after a partial refund | The remainder is split from the module's own record of each refund it sent and the rebuilt order's lines. | The remainder is split from the order and its refunds as Two holds them: their tax subtotals, else their own lines summed per rate. A refund Two lists with neither (one made in the merchant portal without lines) leaves the rest unsplit, and the refund status refuses it with a history note. | OpenCart has no refund record beyond the plugin's own form refunds, so Two's copy is the one record that covers a portal refund too. Refusing is safer than guessing a split. |
| Callback session | The callbacks read the session as it arrives. | A callback that arrives without the session cookie answers with a page that reloads it from the shop itself, keeping the per-order token check on that final hop. The target is rebuilt from the route and the validated order id and token, so it cannot redirect elsewhere. | OpenCart 4.1's session cookie is SameSite=Strict by default, so the redirect back from Two carries no cookie, and OpenCart would otherwise replace the buyer's session (cart and login) with an empty one. |
| Fulfil of an edited order | Order edits are synced to Two, so the order fulfilled is the order as edited. | Order edits are synced to Two the same way. Before fulfilling, the order's own rows (products, totals and addresses as stored on the order) are also compared with a hash kept when Two last accepted them, so an edit Two refused, or one whose outcome is unknown, blocks the fulfil until Two accepts the order as it stands, and the order history says why, pointing to the Two merchant portal when the shop cannot send it. | OpenCart has no record of whether an edit reached Two other than the plugin's own, and fulfilling would otherwise invoice an order the merchant has since changed. Only data the order owns is compared, so catalogue or tax changes alone never block a fulfil. After an edit whose outcome is unknown the order must be rebuilt and sent again, and that rebuild does read the catalogue and tax setup, so there they can. |
| Fulfil and cancel outcomes | The outcome goes to the module log. | The outcome also goes in the order history, at the status the merchant chose, without undoing the status change. | The merchant works from the order page, so a refused fulfil or cancel should be visible there, not only in a log. |

| Partial refunds | A credit slip made on the order page is sent to Two as a partial refund, keyed on the slip. | OpenCart has no credit memo or slip. The Two tab on the order page has a refund form: quantities of the Two order's lines, and an amount line with its net, tax and rate typed. Each refund is a row in the plugin's own table, created before the call and keyed on its id. | The platform has no refund record to hang one on, so the plugin keeps its own. |
| Refund with an unknown outcome | A credit slip is sent once, keyed on the slip; one the module does not send is reported on the order page as not sent. | The refund row is marked unknown and every other refund on the order, the refund status map's included, is refused until the merchant retries it from the Two tab. The retry resends the stored request under the same key. | A second refund made from the form would carry a new key, so Two could refund twice. Retrying under the same key lets Two apply it at most once. |
| Payment terms fee in the cart | The fee is a hidden virtual product added to the cart, at the tax rules group the merchant selects. | The fee is an OpenCart order total (`two_fee`), taxed by the shop's tax engine at the tax class the merchant selects, as core's handling fee is. | OpenCart's order totals are its own way to add a taxed charge, and keep the fee out of the catalogue, stock and product reports. |
| Changing the payment term | The chip saves the term, then the hidden fee product is synced. | The chip saves the term, then OpenCart's confirm view is reloaded (it rewrites the unplaced order) and only its totals rows are swapped in. Placement refuses an order whose stored fee is not the fee for the session's term. | OpenCart writes the order's totals only when it renders the confirm view, so the reload is what puts the new fee on the order. |
| Surcharge percentage bound | The grid's percentage is checked to be a non-negative number, with no upper bound. | The percentage must be between 0 and 100. | Two's fee quote takes the percentage as the share of its fee passed to the buyer and refuses one above 100, so a higher value would only withhold Two at checkout. |
| Company address autofill | Picking a company writes the registry's street, postcode and city into the address form, fits the postcode to the country's format, and writes the registry's phone number into the phone field. | The street, city, postcode and zone are written, as the Magento and WooCommerce plugins do. The phone and the postcode format are left alone. | The buyer's phone is their own contact, which Two checks; a company switchboard number is not a substitute. OpenCart does not validate postcode format, so there is nothing to fit it to. |
| Translations | Module translation files (`translations/<iso>.php`) keyed by a hash of the English source. | OpenCart language files (`language/<code>/...`, the `$_[]` arrays) keyed by name, one set for the admin and one for the storefront, with a CI gate that every locale has en-gb's keys and placeholders. The wording is the reference plugin's wherever the English source matches. | Each platform's own translation mechanism, so a shop's language packs and OpenCart's language switch work as they do for every other extension. |
| Default payment method title | One English default ("Business invoice") stored for every language at install. | No title is stored at install; a language with none set shows its own language file's default. | A buyer in a non-English shop would otherwise see an English method title until the merchant edits it. |
| Product page: placement | The message and the button render from a product page hook the module registers, beside the theme's other product page blocks. | OpenCart 4 has no product page hook. An event on the rendered product page puts them at the end of OpenCart's own add to cart form (`id="form-product"`), under the add to cart button; a theme that replaces that form shows neither, and the log says so once per request. | The only way to place them without editing core files or the theme is the view event, and the add to cart form is the one anchor every OpenCart 4 theme derived from the default keeps. |
| Product page: brand mark | The message and the button show the brand's logo; in the button the logo stands in for the brand word and carries the name as its alternative text. | The brand name is shown as text in both ("Buy with Two"). | The extension ships no brand mark for OpenCart. Text keeps the offer attributed for every buyer and for assistive technology. |
| Buy button: where the buyer lands and what is preselected | After a confirmed add the buyer is sent to the cart; at the payment step the module clicks Two's payment option once. | After a confirmed add the buyer goes straight to checkout. OpenCart lists payment methods in a modal opened with Choose: the first time that list is built, Two's option is checked in place of OpenCart's default (the first method), and the buyer presses Continue as for any method. A method already saved in the session is left alone. | OpenCart's checkout chooses the payment method in that modal, and its add to cart clears any saved method, so checking the option there is the closest equivalent. |
| Buy button: checkout on another origin | With SSL enabled but not everywhere the product page and checkout are different origins: the button still adds to the basket, preselects nothing, and the module logs a warning once per request. | The button records the preselection only when checkout is on the product page's origin, as in the reference plugin, but logs nothing. | OpenCart 4 builds every storefront link from one base URL, with no separate secure one, so the mixed setup the warning describes cannot be configured. |
| Tax codes: the buyer's VAT number | The invoice address's VAT number field. | OpenCart has no VAT number field. The merchant names a text custom field (Order management, Tax) on the address or the account; the order's payment address value is used, else the account's, trimmed. None named means no VAT number. | The closest equivalent: custom fields are how OpenCart shops capture a VAT number, and the value is stored on the order. |
| Tax codes: the merchant's country | The section resolves its own profile of the API key (verify, then the merchant record), held apart from checkout's, and warns when checkout holds another merchant or country. | The merchant record checkout uses, which is already fetched for the key in force and bound to the credentials, gives the country. No separate profile and no mismatch notice. | OpenCart's record cannot describe another key than the one in force, so the two could never disagree. |
| Tax codes: rows and the tax address | Rows per tax rules group: each 0% tax rule; the tax address is PS_TAX_ADDRESS_TYPE. | Rows per tax class: each 0% percentage rate the class's rules use, keyed by class and rate. Step 2 reads the rates OpenCart's own tax engine applies for the order; several 0% rates take their rows' code only when they agree. Step 1's tax address is the shipping address, else the billing address. | OpenCart rates belong to classes through rules, and each rule chooses its own address (shipping, payment or store), so there is no single shop-wide tax address. |
| Tax codes: placement record | Placement records each line's code on the order, and updates and refunds send the recorded codes. | No per-line record is kept: codes are resolved from the mapping each time the order is built (create, the confirm check, an edit). A refund line that references an order line is coded by Two from that line; one that does not (an amount, the rest) at 0% takes the code Two holds on the order's 0% lines when they share one. | The plugin stores no per-line codes, so a change to the mapping after placement can change the codes an edit sends, or refuse the confirm check while the buyer is at Two's checkout. |
